[NUnit](https://nunit.org/) is one of the oldest and most popular testing frameworks for .NET, with a rich ecosystem and extensive documentation.

It has support for all the regular tools you would need in a testing framework, such as running tests in parallel, parameterized tests, and test setup and teardown. In addition, it also has some established extensions in the form of third-party packages.

## Parameterized tests

Many tests are fine to run with the same values every single time. However, you may sometimes want to run the exact same test several times with different values each time. NUnit provides support for this through attributes.

In NUnit, a simple test uses the `[Test]` attribute. For parameterized tests, you can use `[TestCase]` to provide inline data, or `[TestCaseSource]` for more complex scenarios.

### Using `[TestCaseSource]`

`[TestCaseSource]` is less common than `[TestCase]`, but provides more control when you need to generate test data dynamically or reuse test data across multiple tests.

With `[TestCaseSource]`, you specify the name of a static property, method, or field that returns an `IEnumerable` of test cases. The data source can be in the same class or a different class.

## Sharing data between tests

_NUnit docs: https://docs.nunit.org/articles/nunit/writing-tests/setup-teardown/index.html_

A common need when writing tests is to share some common setup between tests. For example, you may want to do some kind of test setup the same way for all tests in a class, or do it only once for the whole class.

NUnit provides several attributes for setup and teardown:

- **`[SetUp]`** - Runs before each test in the class
- **`[TearDown]`** - Runs after each test in the class
- **`[OneTimeSetUp]`** - Runs once before any tests in the class
- **`[OneTimeTearDown]`** - Runs once after all tests in the class have completed

## Running tests in parallel

_NUnit docs: https://docs.nunit.org/articles/nunit/writing-tests/attributes/parallelizable.html_

By default, NUnit will not run tests in parallel. However, you can use the `[Parallelizable]` attribute to enable parallel execution at the method, class, or assembly level.

The `[Parallelizable]` attribute's scope can be set in its constructor, which takes a `ParallelScope` enum. By default, this is set to `ParallelScope.Self`. The values are:

- `ParallelScope.Self` - The test or fixture can run in parallel with others
- `ParallelScope.Children` - Child tests can run in parallel with each other
- `ParallelScope.Fixtures` - Fixtures can run in parallel (this is the default
- `ParallelScope.All` - Everything runs in parallel

For example, with the following test structure:

<FileTree>
  - CalculatorTests
    - AddTests.cs
    - SubtractTests.cs
  - MyServiceTests.cs
</FileTree>

The 3 test classes `AddTests.cs`, `SubtractTests.cs`, and `MyServiceTests.cs` will all run at the same time in parallel by default. However, for each of those test classes, the individual tests inside of them run sequentially.

### Controlling parallel execution

You can use the `[Parallelizable]` attribute to control parallelization behavior:

- `[Parallelizable(ParallelScope.Self)]` - This test/fixture can run in parallel with others
- `[Parallelizable(ParallelScope.Children)]` - Child tests can run in parallel with each other
- `[Parallelizable(ParallelScope.Fixtures)]` - Fixtures can run in parallel (default behavior)
- `[Parallelizable(ParallelScope.All)]` - Everything runs in parallel
- `[NonParallelizable]` - This test/fixture must run by itself
